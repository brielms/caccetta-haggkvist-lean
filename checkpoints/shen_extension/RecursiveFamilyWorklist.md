# Recursive CH family catalog

The mathematical input is a single hypothetical counterexample `Bad ⟨n,r,D⟩` with cutoff `CH.ceilDiv n r`. A `Child p c` carries a proof sending a short cycle in the child back to a short cycle in the parent. This is what permits the counterexample hypothesis to follow that edge. `from_root` runs the catalog before imposing any numerical restriction. Its `ReducedReach` certificate supplies the actual descendant, its own cutoff conditions, and the chain of graph transformations back to the original input. The catalog runs again with both endpoints in scope. Strong induction handles chains whose cutoffs strictly decrease while their degrees change. ## Adding a rule

Register a Lean theorem in the Aesop forward rule set `CHGraphFamilies`. Its hypotheses identify the source family, graph, vertices, and any required inequalities. Use the actual labels and retained graph in the conclusion. The matcher can instantiate the theorem again with a different label or child. The registered head-slot theorem gives a concrete example. For any row with at least $r$ heads and at most $z$ heads outside $T$, the set $N^+(a)\cap T$ contains at least $r-z$ labels. A later rule can use the members of that very set. [Head-slot rule](HeadSlotRules.lean) · [Catalog and matcher](CHForwardCatalog.lean)

To designate a family split, use `ch_family_split_result theoremName` for a theorem's result pattern, `ch_family_split_predicate PredicateName` for a named predicate defined by its alternatives, or `ch_family_split h` for a particular proof. A producer can also return `Branch P` directly. The result-pattern declaration recognizes an existing raw disjunction even when the original producer premises are no longer available. The queue inspects the whole context, including entry facts and results from both engines. Logical disjunctions without a designation stay bundled. Each designated case inherits its witnesses and the original evidence. [Split declarations](CHFamilyDeclarations.lean) · [Queue implementation](CHFamilyWorklist.lean)

For a witness recipe that should fire on every graph or mark carrying a particular kind of evidence, use `ch_on_fact h of Predicate => have result := supplier h ...`. A marked hypothesis supplies the graph and vertices through its actual type. Existing scripts can consume successive outputs under the same role name. The registry records successful instances in each proof context. It uses the rule identity and its actual inputs, including the marked predicate and any substituted roles. Failed attempts are retried when the context grows. A hand-written application is recorded too. Scripts with implicit domain-specific premises still need those premises supplied in a form their Lean terms accept. [Instance matching and receipts](CHContextCatalog.lean)

To inspect the typed catalog after importing the rule modules, run `#aesop_rules CHGraphFamilies` in Lean. Theorems in this index carry proof terms. The worklist's trace identifies the concrete conclusions obtained on each family.

## Repetition and descent

A repeated proposition on the same graph and labels contributes no new fact. A fresh child or a different vertex designation can enable further rules. To rule out a cycle mathematically, a rank may be attached to the actual transitions. One strict decrease followed by a nonincreasing path back is impossible. The well-founded descent theorem covers the stronger situation in which every putative live state forces a smaller live successor. An equal-rank return can remain an open family. [Ranked loop theorems](FamilyLoopLedger.lean) · [Branch and loop tests](FamilyWorklistReplay.lean) · [Reachability split on actual labels](HeadSlotReplay.lean)

## Reading an open frontier

From the repository root in Git Bash, run `bash checkpoints/shen_extension/check_capstone.sh`. With current compiled dependencies, `bash checkpoints/shen_extension/check_capstone.sh --replay` reruns just the capstone. Each run retains its Lean log in its own directory under `.lake/ch-frontier/` and preserves Lean's exit status. When Lean reports open goals as its sole error, the script also writes `frontier.json` there. Each case has its target and a linkable line number for its complete hypotheses. Run `python checkpoints/shen_extension/report_family_frontier.py PATH/Capstone.log --case NAME` to display one verbatim. The index records the log's SHA-256. [Capstone](Capstone.lean) · [Replay script](check_capstone.sh) · [Frontier indexer](report_family_frontier.py)

An empty queue records saturation under the registered rules on the instantiated states. A proof of CH requires every reachable possibility to close, including any family that can recur. The separate degree-eight frontier records which numerical families have already been excluded directly and which move to a lower cutoff. [Degree-eight frontier theorems](GuardedDegreeFrontier.lean)

## Checks for a robustness review

- `two_edits` follows two distinct physical arcs of one graph through two successive repairs. The registry derives all six column bounds. `child_loop` follows the onward edge from the child even when another edge returns to its parent. `degree_nine_child` uses a bound discovered at degree eight to close a descendant at order 33 and degree nine. Its cutoff and numerical premises are computed from the child. The historical file still contains this test, but the current catalog replay leaves that case open. The regression runner skips this file. [Historical replay fixtures](PackingForwardReplay.lean)
- `both_children` leaves both arms of a registered disjunction live. `one_survivor` closes one arm by contradiction. The reachability test repeats this with an actual graph, preserving the target set and the vertex that belongs to it. [Queue tests](FamilyWorklistReplay.lean) · [Graph reach test](HeadSlotReplay.lean)
- `from_root` passes the original bad graph, its reduced descendant, and the certified path between the two as explicit hypotheses to the remaining proof. Check that the final cases still contain `originalBad` and `inputRepairs`. [Entry theorem](RootFamilyEntry.lean)
- `split_on_entry`, `split_from_legacy` and `split_from_typed` start with the parent application of A already present. Each checks two distinct labelled child obligations, applies A on each after its premise arrives, and checks an unchanged repeat. `retained_output_roles` checks that the original consumer of A's output also fires on the new labels while the parent result remains usable. [Symbolic acceptance tests](MarkedRepairReplayTest.lean)
- `second_arc_on_same_graph` starts with two marked arcs on one carrier. The rule initially applies to the first arc only. A new premise enables it on the second arc, and a third pass adds no result. [Test](MarkedRepairReplayTest.lean#L125)
